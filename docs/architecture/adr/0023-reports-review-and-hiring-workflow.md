# ADR-0023: Reports, review and the hiring workflow: one document for the web and the PDF, people's input kept beside the AI's, and a decision only a person makes

- **Status:** Accepted
- **Date:** 2026-10-18
- **Sub-project:** SP-17 (lane A, part A5)

## Context

- **PRD §68 and §69** ask for a proctoring report (14 sections, no unexplained single score) and an interview report (13 sections); **§99** for a candidate-visible report the organisation configures, with internal reports staying confidential; **§71** for eleven review actions; **§72** for nine hiring statuses with every change audited; **§97** for "report viewed", "report downloaded", "recording viewed" and "score modified" in the audit log; **§19, §20 and §98** for Candidate 360, its thirteen tabs and one timeline over eight sources.
- **Master plan §6.13** adds that every report is a web view and a PDF rendered by Playwright, stored in `report_exports`, and that a recruiter approves each candidate-visible release.
- **Earlier parts left the data.** ADR-0031 stores evaluations with verified evidence and never edits them; ADR-0032 keeps dismissed events in the report; SP-12 keeps recordings with timeline maps and audits playback; SP-07b left a placeholder page for the candidate's report.
- **The AI must not decide** (§3.2(1)). A score a person disagrees with, a recommendation and the final decision all need a place that doesn't overwrite what the AI said.

## Decision

- **A report is a document of blocks** (`hirevion_core.reports`): sections of `text`, `list`, `facts`, `table`, `quotes`, `notice` and `code` blocks, every cell already formatted. Each section says `populated`, `empty` or `pending` and why. The web's `ReportView` and the PDF's HTML are two renderings of that one document, so a section has one source and a PDF cannot show what the web view doesn't. Text is English for now; the document carries no UI strings the web would translate.
- **The PDF:** Jinja2 with autoescape renders the document to standalone HTML with a no-network content-security policy; Playwright's Chromium renders it with JavaScript off and every request aborted; the PDF and its SHA-256 are stored (`{org}/interviews/{id}/report/…`, `report_exports`) with the SHA-256 of the document it came from. Chromium missing means `503 pdf-unavailable` and the web view still works. Two renders run at once at most.
- **Five reports:** interview (13 §69 sections), proctoring (14 §68 sections, counts per severity and review outcome, the server's reason for each severity in words, evidence as references, and an explicit statement that there is no single score), coding (what the interview recorded; SP-16 fills test results and grading and the pages say so), internal candidate (the 360 as a document) and candidate-visible.
- **The candidate-visible report is a separate path.** The organisation chooses which of §99's five items may ever be shown (`organization_settings.candidate_report`, default completion and next step); a draft is written from the evaluation in plain words with no scores, flags, notes or proctoring; a recruiter edits it and approves (`reports.release`); approving freezes the allowed, included items into `reports.released_items`; the portal reads only that and never a note, a score change, an input, a proctoring event or a recording. Withdrawing hides it again with a reason. The portal's PDF is rendered from the released items and kept by the document's hash.
- **Views, exports and downloads are audited:** `report.viewed` (once per five minutes per person and report, like proctoring's), `report.exported`, `report.downloaded` (every download, the candidate's own included, with `actor_type = candidate`), `report.released`, `report.withdrawn`, `recording.viewed` for each play of the review workspace's media, `score.modified`, `proctoring.event_reviewed` (existing), `candidate.note_added`, `hiring.input_added`, `hiring.status_changed` and `hiring.decided`.
- **People's input never edits the AI's.** `score_changes` is insert-only: the latest change of a score is the one in force and shows beside the AI's with the reason and who made it; a skill's change does not recompute the overall score. Notes (`candidate_notes`) and Hiring Manager input (`hiring_inputs`) are insert-only too, the latest input per author counting; input never moves a status.
- **The hiring status (§72) is stored beside the screening stage** (`applications.hiring_status`, every change in `application_status_history`). `record_stage` syncs it from the stage (a person's stage action names them), `lifecycle.transition` from the interview (`interview_started`, back to `interview_invited` when abandoned, `interview_completed`), and a person moves the rest with a reason where one is needed. `interview_invited/started/completed` are facts and cannot be chosen. **`selected`, and a rejection after an interview, are the final decision:** they need `hiring.decide` (organisation admins and recruiters), a reason and, for `selected`, a finished interview; the system never moves a `selected` application and only someone who may decide can reverse one. A rejection before any interview is the screening action as before. The decision tab of the candidates list holds decided applications, and "completed" no longer does.
- **The review workspace has one clock:** milliseconds from the interview's start (the transcript's own origin). A recording's timeline map turns it into a file position and back (`review/sync.ts`, tested), a missing segment is a gap with no position, and one leader track drives the others, resynchronised past 400 ms of drift. The workspace's media call returns each track's map inline with five-minute read links and is audited on every play; a link that expires is asked for again.
- **Candidate 360 loads what the reader may see:** `GET /candidates/{id}/360` leaves out interviews, proctoring and recordings for a reader without `reports.interview.view`/`reports.proctoring.view`; the web hides those tabs. `GET /candidates/{id}/timeline` unifies screening, interview, transcript, coding, proctoring, recording, evaluation and recruiter actions, newest first, filtered by source and by what the reader may see, and pages by time.
- **Permissions added:** `reports.export`, `reports.release`, `reports.score.modify`, `hiring.input` and `hiring.decide`. Adding a note needs `reports.interview.view` (on an interview) or `candidates.view` (on a candidate).
- **The pipeline's move is the status change.** A card's "Move to" menu (and dragging, for those who can) calls `POST /applications/{id}/hiring-status`; a move that needs a reason or is a decision asks first.
- **The simulator is the desktop for the golden path:** `hv interview-sim` also opens a proctor session, sends a scripted event for each event section of the report, a heartbeat and recording segments; `hv audit-tail` prints the audit log for the end-to-end suite.

## Consequences

- **One source per section:** a report section changes in one place and both renderings follow; the cost is that report text isn't translated until the document carries message keys.
- **Chromium becomes a runtime dependency of the API** (Python Playwright pinned to the Node suite's version so the browsers installed for end-to-end tests serve both). Production images need `playwright install chromium`; the cloud plan sizes it. Rendering is inline in the request (about a second); a queue is the way out if exports become heavy.
- **Nothing the AI said is lost:** every number a person changed is on record beside the AI's, and the evaluation stays reproducible (ADR-0031).
- **The candidate can't see more than was approved**, even if the evaluation, the draft or the hiring status changes afterwards; the cost is that fixing a typo in a released report means withdrawing and releasing again.
- **Watch:**
  - the draft's wording (it is a convenience for the recruiter, never an AI verdict sent unreviewed);
  - the audit volume of `recording.viewed` (every refresh of the workspace's links is one);
  - the interview report's size for long transcripts in a PDF.
- **Hand-offs:** SP-16 fills the coding sections; SP-18 can deliver `report.ready` when a release or an evaluation completes; SP-21 reads `application_status_history` for the funnel; SP-22 adds retention for `report_exports` and an audit-log viewer, and the policy editor for what a proctoring report may show.
