# SP-00c Voice-Latency Spike Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Measure the real voice loop — candidate stops speaking → AI starts speaking — through the local LiveKit server with Deepgram (speech-to-text and text-to-speech) and Gemini (LLM, via its OpenAI-compatible endpoint), choose the models that keep p95 ≤ 2.5 s, and record the result in ADR-0005. The agent code stays as the seed of `backend/interview_agent` (SP-09).

**Architecture:** A new uv workspace member `backend/interview_agent` (package `hirevion_interview_agent`) runs a LiveKit Agents worker: Silero VAD, the LiveKit turn detector, `deepgram.STT`, `openai.LLM` pointed at Gemini's OpenAI-compatible base URL, and `deepgram.TTS`. Its settings (URLs, keys, model names) are a pydantic-settings class reading the root `.env`. A separate benchmark, `tools/voice_bench` (package `hirevion_voice_bench`), joins a room as a synthetic candidate with the LiveKit Python SDK, publishes a pre-rendered spoken answer as a microphone track, and timestamps the first non-silent audio frame from the agent. The agent also logs the framework's per-stage metrics (end-of-utterance delay, STT, LLM time-to-first-token, TTS time-to-first-byte) so the total can be broken down.

**Tech Stack:** LiveKit Agents (Python) with the `deepgram`, `openai`, `silero` and `turn-detector` plugins; the `livekit` and `livekit-api` Python SDKs; pydantic-settings; numpy for audio analysis.

## Global Constraints

- Everything in `MASTER_IMPLEMENTATION_PLAN.md` §13 and the SP-00a/SP-00b constraints applies.
- Model names come from settings (`HV_LLM_MODEL_FAST`, `HV_STT_MODEL`, `HV_TTS_VOICE`), never literals in logic; defaults are chosen from `uv run hv doctor`'s model list.
- Synthetic speech only (generated by Deepgram TTS from fixed scripts); no real candidate audio.
- Each benchmark run is bounded (default 20 turns) and prints its vendor usage so the spend is visible.
- Before writing agent code, read the installed LiveKit Agents version's docs (package README / `help()` on `AgentSession`, `Agent`, `WorkerOptions`, metrics events); the API evolves between releases.

### Task 2: The spike agent

- [ ] Add dependencies (LiveKit Agents with the deepgram, openai, silero and turn-detector plugins) and download the plugin model files once (`uv run python -m hirevion_interview_agent.agent download-files`).
- [ ] Implement `agent.py`: an `Agent` whose instructions keep replies to one or two short sentences; `AgentSession` with Silero VAD, the turn detector, `deepgram.STT(model=settings.stt_model)`, `openai.LLM(model=settings.llm_model_fast, base_url=settings.llm_base_url, api_key=settings.gemini_api_key)`, `deepgram.TTS(model=settings.tts_voice)`; log every metrics event through the collector; greet with one fixed question.
- [ ] Run it against the local LiveKit (`uv run hv up` first) and talk to it once from the LiveKit Agents Playground or the benchmark to confirm the loop works end to end.
- [ ] Commit `feat(agent): add voice-latency spike agent`.

### Task 3: The synthetic-candidate benchmark (TDD for the pure parts)

- [ ] Tests first for `audio.py`: RMS energy of silent vs. tone frames; `first_voiced_frame()` finds the first frame above a threshold; 16-bit PCM WAV round-trip.
- [ ] Implement `audio.py`, then `bench.py`: render N fixed answers with Deepgram TTS to WAV (cached on disk under `tools/voice_bench/.cache/`, gitignored); create a room and a candidate token with `livekit-api`; join with the `livekit` SDK; wait for the agent's first question to finish; publish one answer through an `AudioSource`; record `t_end` after the last frame; subscribe to the agent's audio and record `t_first` at the first voiced frame; repeat; print p50/p95/max and the per-stage breakdown from the agent logs.
- [ ] Commit `feat(tools): add voice-latency benchmark`.

### Task 4: Measure and decide

- [ ] Run 20 turns for each candidate configuration: Gemini fast models listed by `hv doctor` × Deepgram STT (`nova-3`, and `flux` if the account has it) × two Aura-2 voices; record p50/p95 and the stage breakdown.
- [ ] If an OpenAI key is present, repeat the best configuration with an OpenAI fast model for the production baseline.
- [ ] Write ADR-0005 with the table, the chosen defaults, and follow-ups (e.g. a spoken acknowledgement while the analyzer runs, speculative next questions — master plan §6.8).
- [ ] Set the chosen defaults in `.env.example`; commit `docs: record voice-latency measurements and model choices`.
