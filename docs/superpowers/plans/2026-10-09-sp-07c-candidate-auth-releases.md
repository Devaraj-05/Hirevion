# SP-07c Desktop Candidate Auth and Releases Implementation Plan

**Goal:** PRD §8 (desktop), §26 (version check) and §28, implementing `docs/api/contracts/candidate-auth.md` exactly. The work:
- Sign-in from the desktop with §28's six checks, an emailed one-time code on a new device, and device-bound tokens (DPoP, RFC 9449).
- A 10-minute access token, a rotating refresh token (8 hours absolute, reuse revokes the family) and an interview-session token.
- The desktop release registry: channels with a minimum version, releases with staged rollout and signatures, the version check and the Tauri update manifest, and its platform page.

**Architecture:**
- **`hirevion_core.candidate_access.dpop`:** proof verification: ES256 only, `htm`/`htu`/`iat`/`ath`, the RFC 7638 thumbprint, and the replay cache in Valkey.
- **`hirevion_core.candidate_access.tokens`:** the signing key, access and session JWTs, refresh families.
- **`hirevion_core.candidate_access.service`:** sign-in, codes, refresh, sign-out, the interview list and session tokens.
- **`hirevion_core.desktop.releases`:** versions, channels, rollout buckets, the check and the manifest.
- **The API:** `/candidate-auth/*` (DPoP-guarded, never a cookie), `/desktop/*` (public), `/platform/desktop-releases` and `/platform/desktop-channels` (super admin), `/organization/candidate-access` (the new-device code setting).
- **The web app:** `/platform/desktop-releases`, and the new-device code switch on the organisation page.

## Decisions (defaults; the product owner asked to build without stopping)

- **Proofs:** ES256 with a P-256 `jwk` in the header (no private parts, no other algorithm); `iat` within ±60 s; `jti` at most 64 characters and unseen for 5 minutes per key (Valkey `SET NX EX 300`); `htm` the method; `htu` the request URL without query or fragment, compared on scheme, host and path. The server asks for no nonces yet. Every failure is `401 dpop-invalid`.
- **The signing key:** an ES256 key from `HV_CANDIDATE_TOKEN_KEY` (base64 PKCS #8, generated by `hv init-env`/`env-sync`). Outside production a missing key is replaced by one generated at start-up, with a warning (tokens then die with the process).
- **Access token:** `iss` (the API), `aud` `hirevion-desktop`, `sub` the candidate account, `org`, `scope` `candidate`, `cnf.jkt`, `sid` (the refresh family), `iat`, `exp` (10 minutes), `jti`.
- **Session token:** the same with `scope` `interview` and `interview_id`; `exp` is the earliest of the window's end plus the interview's duration (so one started late in its window can finish), now + 4 hours, and the family's end. Every request with either token checks the family hasn't been revoked, so sign-out and reuse detection take effect at once.
- **Refresh tokens:** `rt_` + 256 random bits, stored as SHA-256, bound to the device; one family per sign-in, 8 hours absolute; each use rotates; using a spent one revokes the family (`refresh-reused`) and is audited.
- **Devices:** a key's first verified sign-in registers it (`candidate_devices`: thumbprint, public key, name, app version, OS). With the organisation's "code on a new device" on (the default), an unverified key gets a 6-digit code by email (`candidate_otps`, HMAC-SHA-256 under a key derived from the signing key, 10 minutes, 5 attempts, a resend at most every 60 s and 5 in all).
- **§28's six checks,** in the contract's order:
  1. the app version against the channel's minimum (`426 app-update-required` with `minimum_version` and `download_url`);
  2. the account and password (`401 invalid-credentials`, the same for unknown emails after the same argon2 work; `423 account-locked` with `Retry-After` after the recruiter lockout's rules);
  3. an assigned interview the candidate has been invited to (`no-interview`);
  4. its job open (`job-closed`);
  5. its status invited, in progress or interrupted (`interview-not-available` with `status`);
  6. its window not over (`interview-expired` with `expired_at`).

  Checks 3 to 6 run over every interview, and the sign-in succeeds when one passes them all; the answer lists those. A person with accounts in several organisations signs in to the one whose password matches and which has an interview to take (the soonest).
- **Releases:** semantic versions; channels `stable` and `beta`, each with a minimum version; releases per channel and architecture (`x64`, `arm64`) with notes, URL, minisign signature, status (`draft`, `published`, `withdrawn`) and a rollout percentage. A device is inside a partial rollout when `sha256(jkt:version)` falls in the first `rollout`% (no proof: only full rollouts). The update manifest is Tauri v2's, answers `204` when nothing newer applies, and never offers a downgrade. Release changes are audited in the platform log.
- **Rate limits:** sign-in, code and refresh routes per IP and per email or challenge, failing closed like recruiter sign-in.
- **Audit (the candidate's organisation):** `candidate.login.succeeded`, `.failed`, `.locked`, `candidate.otp.sent`, `.verified`, `.failed`, `candidate.device.registered`, `candidate.token.refreshed`, `candidate.token.reused`, `candidate.logout`, `candidate.session_token.issued`.

## Tasks

1. **Schema (migration 0014):** devices, codes, refresh tokens, releases and channels, the organisation's candidate-access settings, the refresh and code lookups. Isolation and models-match tests.
2. **Proofs:** the verifier and thumbprint, with tests for every refusal (alg, typ, jwk, signature, htm, htu, iat, replay, ath, key mismatch).
3. **Tokens:** signing, verification, families and rotation, reuse revocation. Tests.
4. **Sign-in:** the six checks in order, accounts in several organisations, lockout, codes (verify, resend, limits), refresh, sign-out, `me`, session tokens. Tests.
5. **Releases:** versions, the check with rollout, the manifest, the platform API. Tests.
6. **API:** the routes and their DPoP guard, rate limits, the matrix's unguarded list, OpenAPI and codegen.
7. **Web:** the releases page and the organisation's switch. Component tests.
8. **End to end:** a Python script-level test drives the whole contract (sign-in → code from Mailpit → `me` → session token → refresh → reuse refused → stolen token without the key refused → outdated version refused); ADR-0021, runbook, threat model, Appendix A (§8, §26, §28), PENDING_TASKS.md.
